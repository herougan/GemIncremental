# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Gem Incremental TD — a Unity 6 (6000.5.6f1) tower-defense game where the player iteratively builds a defense from randomly-rolled gem turrets, layered on top of an incremental/idle currency meta-layer and enhancement system. Combat/entity code is under `Assets/Scripts/TowerDefence/`; the meta layer spans `Assets/Scripts/Incremental/` (currency) and `Assets/Scripts/Player/` (Player, Foundry, Compendium, ArtefactCollection, ...).

Currency (`Incremental/Currency/Currency.cs`) is a `ddouble`-backed `Name`/`Symbol`/`Amount` object. The base currency (gold) is intended to scale enormously — 1,000,000 copper → 1 silver, 1,000,000 silver → 1 gold, up into the trillions and eventually toward `1e10,000` gold — which is exactly the incremental-scale range `ddouble` exists for (see below). Wired into combat as `Player.Gold`: awarded on Monster death (`StatType.Reward`, scaled by `WorldProgress` alongside Health/Attack/Defence) and spent in the Upgrade Menu (see below) — only tiers above plain "Gold" (copper/silver) don't exist yet.

## Commands

No CLI test suite yet (`Assets/Scripts/Util/Test/thoughts.txt` is design notes, not test code; no `.asmdef`/PlayMode/EditMode assemblies). Building/running the game happens through the Unity Editor.

For a quick compile-error check without opening the Editor:

```
dotnet build "Assembly-CSharp.csproj"
```

Scope to `Assembly-CSharp.csproj` specifically, not the full `.sln` (which also builds every Unity package's own slow, noisy `.csproj`). Only errors/warnings under `Assets/Scripts/` are actionable. `Assembly-CSharp.csproj`/`.sln` are regenerated by the Editor on domain reload — new `.cs` files need an Editor reload (or a temporary manual `<Compile Include>`) before `dotnet build` sees them.

**Always delete `obj`/`bin` before trusting a `dotnet build` result** (`rm -rf obj bin && dotnet build ...`, or pass `--no-incremental`). A plain incremental `dotnet build` in this repo has repeatedly reported "0 errors" on a build that a clean rebuild immediately shows *does* have real errors (missing-`using` CS0103s, an interface-diamond CS0121, a wrong enum member, a protected setter) — confirmed by deleting `obj`/`bin` and rebuilding, which surfaced 6 genuine pre-existing/newly-introduced errors an incremental run had missed in a row across multiple checks. Don't rely on an incremental result to mean the code is clean.

A package added to `Packages/manifest.json` (e.g. `com.unity.localization`) also needs an Editor reload to actually resolve before its types compile.

## Architecture

### Entity system

`Entity` (`TowerDefence/Entity/Entity.cs`) is the base simulation object for anything alive in combat — owns `StatBlock`/`ElementBlock`, `Tags`, lists of `Buffs`/`Skills`/`Statuses`/`TowerAuras`/`MonsterAuras`, and a large set of events looked up by `TriggerType` (`GetEvent`/`SubscribeEvent`/`RaiseEvent`) rather than one field per event. `EntityController : MonoBehaviour` is the Unity-side wrapper (owns an `Entity`, registers it into `EntityManager`'s Position Registry); `Monster`/`Tower : Entity`, specialized through `MonsterPlan`/`TowerPlan` data rather than code.

**Global event bus**: `Util.Events.EntityEventBus` (static, no bookkeeping) is what `Entity.RaiseEvent` publishes every single event onto. Two ways to subscribe: `Subscribe(TriggerType, handler)` (only invoked for that exact type — what `EntityWaveManager`/`BattleTracker` use, since they each only ever cared about one or two TriggerTypes and used to run-then-bail on every other event in the game) and `OnAnyEvent` (genuinely global observers that want *everything* unfiltered — `GameManager`'s event-count tally, `EntityManager`'s own `recentEvents`/`eventCounts` bookkeeping; a real requirement for those two, not a filtering gap). `Util.Events.PlayerEventBus` is the same shape for Player-meta events — stub, nothing publishes to it yet.

### Skills / Effects / Triggers / StatMods

**game event → `RaiseEvent` → `EntityEventBus.Publish` (global) + `WrappedAction` (per-skill, via the Entity's own `TriggerType` dictionary) → `EffectController.ApplyAction` → `IActionHandler`.**

- **`Trigger`**/**`TriggerContext`** — `Trigger` is *when* (data only); `TriggerContext` is one flat payload class carrying every optional field (`Entity`, `Target`, `Stat`, `Damage`, `Source`, `SourcePosition`/`TargetPosition`, ...) any event might need — a per-TriggerType context hierarchy was tried before and abandoned (see the commented-out interfaces at the bottom of `TriggerContext.cs`).
- **`Effect`** bundles `Triggers` + `Conditions` + `Actions`, each a `[SerializeReference] List<I...>` (Unity can't serialize through a plain interface reference at all). **Every concrete `IAction`/`ICondition`/`ITrigger` implementation needs its own `[Serializable]`** — inheriting it from a `[Serializable]` base (`Action`, `Condition`) is not enough, since `SerializeReference` keys off `obj.GetType()`. Forgetting it on a new subclass doesn't fail loudly: content built and tested in the same Editor session looks fine, then silently loses that subclass's extra fields (falls back to the base class) on the next domain reload — this exact bug shipped once (`ProjectileAction`/`SpawnAction`/every `Condition` subclass), caught only when a rebuilt Tower's `ProjectileAction.Plan` came back null. Conditions are evaluated by `Util.Game.EntityUtil.Check` (the one place `ICondition`s are evaluated — not on `Condition` itself).
- **`Action`/`IActionHandler`** — `Action` is one pigeon-holed data class (`ActionType` discriminator + per-type fields); handlers live under `Effects/Types/Attack/`, `.../Stat/`, `.../Spawn/`, dispatched by `EffectController.ActionHandlers`. Implemented so far: `Stat`, `Damage`, `Reflect`, `Revenge`, `Projectile`, `ApplyBuff`, `Spawn` (`SpawnAction.SpawnSelf` spawns a scaled-down copy of whatever Entity triggered it — e.g. a Slime "splits on death" — rather than a fixed `MonsterPlan`, so one SkillPlan asset works unchanged across species; gated by `CounterType.SplitDepth`, see Conditions below).
- **Conditions** gained a generic **Counter**: `ConditionType.Counter`/`CounterCondition` + `Entity.GetCounter`/`SetCounter`/`IncrementCounter(CounterType)` — an author/handler-settable per-Entity int (unlike `Mileage`, which only ever accumulates). `CounterType.SplitDepth` is the only value so far.
- **`WrappedAction`** subscribes a handler onto an Entity event or a periodic `CountdownTimer`, remembering which `Skill` owns it (`Ref`) for later detach; its `Invoke` also stamps `TriggerContext.Source` with that skill if nothing more specific already set it — this is how `Damage.Source` (and battle-tracking/attribution) ever gets populated.
- **`Skill.RegisterCallbacks()`/`Deregister()`** are the *only* place a Skill/Buff goes live/dies — each also calls `ApplyPassive()`/`UnapplyPassive()` (see StatMods below), so registering/deregistering a Skill is the single action that wires triggers **and** stat contributions together. `Entity.RegisterSkill`/`DeregisterSkill` are the canonical entry points (`RegisterSkills()` runs once, at Spawn, over InitSkills/Buffs/Statuses/Auras).
- **`Buff : Skill`** adds `Duration`/`Time` (ticked from `Entity.Tick`) and fires `OnExpired` once `Time >= Duration`; `Entity.ApplyBuff` subscribes to that and cleanses itself. Same `BuffType` re-applied refreshes `Time` (StatBuff/Aura/Saga) or calls `Stack()` (StatusBuff — see Status Stacking below) rather than double-applying. `Buff.Create(plan, caster)` is the one place a runtime object gets built from a `BuffPlan` (both `Entity`'s `InitBuffs` and `ApplyBuffActionHandler` route through it) — returns a real `Aura` if `plan.IsAura`, a plain `Buff` otherwise.
- **Aura propagation** (`Aura.cs`/`AuraPropagationService.cs`) — real now, not a stub. `AuraPropagationService` is the "responsible party": only entities that actually own a live (non-instance) Aura are tracked (reference-counted `Register`/`Unregister`, hooked from `Aura`'s own `RegisterCallbacks`/`Deregister` overrides), and each tracked source gets exactly **one** `EntityManager.GetEntitiesInRange` call per tick interval (`0.25s` default, not every `TickManager.OnTick`) covering every Aura it owns at once (sized to the widest `Range` among them) — "one round of checking to satisfy all of them." Each `Aura` then filters that shared candidate list down to its own `Range` and does its own conditional-grant/enter/exit bookkeeping (`Aura.Propagate`/`PassesConditions`, reusing `Effect.TargetConditions` off the Aura's own Plan — no separate Aura-specific condition system). A candidate that qualifies gets an `IsInstance=true` copy via `Entity.ApplyAuraInstance`, routed into `TowerAuras`/`MonsterAuras` (not `Buffs`) by who cast it — that list membership *is* "known to come from an Aura, not another Skill type," no extra marker needed. Leaving Range either cleanses immediately or, if `BuffPlan.AuraLingerDuration > 0`, converts the instance into a normal timed Buff for that many more seconds (`IBuff.SetDuration`) that expires on its own. `AuraSpreading` (an aura-satellite relaying the Aura further, chained outward) is still an unbuilt stub — only the source's own non-instance copy ever registers with the service.
- **Status stacking** (`Buff.Stack`/`BuffStackType`/`SkillsLib.StatusStackTypes`) — a `(TimeOperation, RankOperation, ValueOperation)` triple of `MathOperation`s (see `MathsLib.Operate`) combines the reapplied and existing `StatusBuff`'s Duration/Rank/Value; `Entity.ApplyBuff`'s StatusBuff branch calls `Stack()` (not the plain `AddStack()` counter-bump it used to), which now does both the numeric combination *and* increments `Stacks`. Four named archetypes exist as a starting point, not a final balance pass — `FireType` (Max/Max/Add — duration takes the longer application, value keeps adding), `Poison` (Add/Max/Max — duration extends, value takes the strongest dose), `Debilitating` (Max/Max/Max — CC-adjacent, no compounding), `Disease` (Nothing/Add/Max — duration untouched, rank keeps climbing); every `StatusType` is assigned one. `SkillsLib.GetStatusPlan(type)` prefers a real `Resources/Status/<type>` `BuffPlan` asset but falls back to an in-memory placeholder (logged) instead of the null `Resources.Load` used to silently return — constructing a `StatusBuff` no longer crashes just because no one has authored real Status content yet.
- **StatMods** (`Entity/Stats/StatMod.cs`) — `IStatMod` (`StatType`, `ddouble Value`, `Operation`, `Source`) is how *any* source (a Skill's Passives, Foundry, a direct `ActionType.Stat`) permanently modifies a stat. Registered into `Entity`'s own `Dictionary<StatType, List<IStatMod>>` (not on `StatBlock`/`Stat`) alongside a dirty-flag set; `Entity.GetStat(type)` only recomputes (`Util.Game.EntityUtil.ApplyStatMods` — Add mods, then Multiply, then Exponent, bucketed by `Operation` so result order is independent of registration order) when that `StatType` is dirty, otherwise it's a cached O(1) read. `ActionType.Stat` mods are permanent (no owner ever deregisters them); a Buff's Passive-driven mods are removed automatically when the Buff expires/is cleansed.
- **`IEnhancementSystem`** (`Player/EnhancementSystem.cs`) — shared contract (`ApplyModTo(IEntity)` + `GetMods()`) for Player-owned systems that permanently modify an Entity **at spawn** (distinct from the always-live StatMod stacking above): `Foundry` today, with `Achievements`/`Compendium`/`Forge`/`Collection`/a Research Centre expected to join it. `EntityManager` collects every registered system's `GetMods()` into one cached list (`RegisterEnhancementSystem`/`MarkEnhancementsDirty`/`ApplyEnhancements`), recomputed only when a system signals it changed.

### Stats system

`Stat` (`Base`, `Value`, both set equal at construction) → `DepletableStat` (`Current`/`Deplete`) → `RegenerableStat` (`Regeneration`/`Tick`/`Rest`). `StatBlock` is the per-entity raw storage (`GetStat`/`GetBase`/`SetStat`/`SetBase`/`GetCurrent`) — it no longer decides what a stat's *effective* value is on its own; `Entity.GetStat` (StatMods layered on `GetBase`) is the authoritative read.

`ddouble` (`Util/Maths/MathsLib.cs`) is the incremental-scale `(Mantissa, Exponent, Precision)` struct used everywhere a game-balance number needs range beyond `double`. `+`/`-`/`*`/`/`/`^`(power) all operate on mantissa/exponent directly and are safe at extreme scale (`^` was fixed to use the exponent operand's *full* value, not just its mantissa — safe well past `1e100`). `MathsLib.Exp`/`Log10`/`Ln`/`Log` are similarly mantissa/exponent-safe (never overflow through a `double` intermediate); `Sin`/`Cos`/`Tan` are plain `double`-conversion wrappers, deliberately *not* safe for astronomical inputs (trig of a googol-scale angle isn't a meaningful game value). `PrettyPrint()` is the human-facing formatter (plain+commas below a million, `K`/`M`/`B`/`T`/... above) — distinct from `ToString()`, which is mantissa-e-exponent and meant for huge currency displays. `ddouble.ZERO` is a `static` field, not a compile-time constant — use `default(ddouble)` for a zero-valued default parameter.

### Manager layer

`GameManager` (singleton `MonoBehaviour`) owns `Player`, `WorldProgress`, and `RoundManager` (a convenience accessor to that singleton), subscribes to `EntityEventBus` in `Start()` and re-broadcasts as its own named events (`OnMonsterDeath`, `OnMonsterHit`, ...) — the triggerer never knows GameManager exists; also where Monster-death Gold gets awarded (see Currency above) and one of `DamageCalculator`'s roots (`IDamageModifier`). `EntityManager` is the entity registry/wiring hub + Position Registry (`IEntity ↔ Transform`, since plain-C# `Entity` carries no position itself) + the Enhancement cache above + `GetAllEntities()` (a snapshot list `TickManager` ticks every fixed step). `EntityWaveManager` is *the spawner* — decides wave timing/quantity (`WaveUtil.ENEMIETRIX`: `Biome → Stage → Round → Wave → SpawnChain`, 20 each) and calls `EntityManager.SpawnMonster`; exposes `MonstersRemainingToSpawn`/`MonstersAlive` (decremented on either `OnDeath` or `OnReached` — see Map below). `RoundManager` sits above it, timing the gap before the next wave (or the longer respite between rounds) once a wave's monster count hits zero.

`TowerDefence.Manager.TickManager` (singleton) is the global fixed-timestep tick loop — drives every registered Entity's `Tick(dt)` plus a public `static event Action<float> OnTick` for anything else needing the same synced dt (Monster movement subscribes here), all from `FixedUpdate` rather than `Update`/`Time.deltaTime` specifically so a step is the same size regardless of render framerate (also what would make a future "fast-forward N ticks with no render" trivial). Nothing auto-creates it — it has to be present in the scene like every other manager.

`Util.Game.EntityUtil` is pure calculation from parameters only (no manager/singleton reaches) — condition checking, `ApplyStatMods`, DPS estimate, `Mitigate` (diminishing-returns defence formula — `Entity.ApplyDamage` picks `Defence` vs `MagicResist` by whether the hit carries `Tag.Magic`, same reading the Nullifier absorb step already used). `Util.Game.BattleTracker` aggregates damage-by-(attacker, skill) off `EntityEventBus` for a battle-report readout, plus `GetDPS()` (total tracked damage / seconds since the last `Reset()`).

### Map / Pathfinding

`TowerDefence/Map/`: `MapPlan` (asset, raw placeholder-format string + `LaneAssignments`) → `MapGenerator.LoadMap` → `Map` (pure grid data, `TileType`: `Floor`/`Wall`/`Buildable`/`Source`/`Destination`) → `MapGenerator.BuildGamespace` (visual tiles — one shared `TilePrefab` instantiated per cell, tinted per `TileColors`, not a prefab per `TileType`) — same data/visual split as Entity/EntityController. `MapGenerator.GenerateRandomMap` procedurally carves an alternative to a hand-authored `MapPlan`.

`PathUtil.FindAllPaths` resolves every Source to a route via Dijkstra; a Source/Destination's `TileData.Lane` (`int?`) makes this general beyond one Source/Destination pair — untagged (`null`) Sources/Destinations share one any-to-any pool, a numbered Lane pairs *only* with the same number (no fallback). `MapGenerator.BuildPaths` converts the result to world-space `Dictionary<Vector2Int, List<Node>>` (keyed by Source position) — a spawner hands the whole `List<Node>` to `MonsterController.SetPath`, which walks it via `TickManager.OnTick` (fixed-step, so movement is framerate-independent the same way Entity.Tick is) and raises `TriggerType.OnReached` on arrival (distinct from `OnDeath` — reaching the Destination isn't being killed). `MonsterController.RemainingNodes` (Nodes left before the Destination) is what `TowerController`'s `Targetting.distance` sorts candidates by — reached via `EntityManager.GetTransform(entity).GetComponent<MonsterController>()`, since the Tower only ever holds the plain-C# `IEntity`, not the Component.

### Fusion / Mulligan

`TowerPlan.ingredients` (a multiset — duplicate entries mean "more than one of this") is a fusion recipe; `Util.Game.FusionUtil.FindCombinables(hand, field, allRecipes)` matches it against a Mulligan hand + placed Towers, hand-items-first. A recipe fully satisfiable from the hand alone becomes an extra pick option; one needing field Towers too is detected (`FusionMatch.FromField` — every candidate Tower per still-open ingredient slot, not one pre-chosen one) but not yet auto-consumed (STUB — which duplicate gets consumed, and that it should be placed atop the consumed Tower's own position, are both decided-but-unbuilt). `Player.Mulligan` is just `Choices`/`Reroll(pool)` — no token cost (unlike an earlier prototype's version), no runtime `TowerPlan` registry yet (`AvailableTowers` is manually assigned per scene).

Multi-tier recipes ("Ruby T1+Sapphire T1+Emerald T1 = Electrum T1, and T2 versions give Electrum T2") need zero `FusionUtil` changes — since it matches by exact `TowerPlan` reference, authoring one `TowerPlan` asset per tier with that tier's own `ingredients` list (linked via the below `NextRank`) makes the rule fall out for free.

### Upgrade Menu

`UpgradeMenu` (tabbed, IMGUI) sits outside/on top of the in-run UI — `UpgradeCentre` is the only real tab so far (`Foundry`/`Compendium`/`Achievements` are labelled placeholders); opens either standalone or by clicking a placed Tower (no collider system exists, so this is a screen-space nearest-Tower-to-click check, not a raycast). `Util.Game.TowerUpgradeUtil` (pure calculation, `Player` passed in as a parameter) does the actual spending: `PurchaseStat` registers a permanent `StatMod` per purchase (cost scales with `Tower.UpgradePurchases[stat]`, runtime-only, resets per spawned instance); `TowerPlan.SkillUnlock { Threshold, Skill, Cost }` gates a Skill behind total purchase count, then still needs its own separate Gold spend (`PurchaseSkill`) to actually register.

**Ranking is a deliberately separate, not-yet-built mechanic** from both of the above — `TowerPlan.rank`/`NextRank`/`PreviousRank` exist (from an earlier prototype) but nothing currently reads/writes them; how a Tower advances tiers in the first place (so its higher-tier form can feed a fusion recipe) is still an open question.

`MainMenu` is the top-level "above the game" nav bar (a persistent IMGUI strip across the top of the screen, not a separate scene). Its first button is a "return to the game" control labelled with *where* the game currently is rather than a fixed name - "Field N-M": Field = `WorldProgress.Biome`, N = `Stage`, M = `Round` (1-indexed for display), read live every frame; clicking it closes `UpgradeMenu` (the only other "page" so far) since the base game panels are always drawn underneath regardless. "Upgrades" opens `UpgradeMenu` with no Tower pre-selected. 6 more buttons are disabled placeholders reserving layout for undesigned destinations.

### In-Editor tooling

`Tools/TowerDefence/Entity Data` (`Assets/Scripts/Editor/EntityDataWindow.cs`) is a UI Toolkit `EditorWindow`: lists every `IPlan`-implementing type via `TypeCache` reflection (so any new `IXPlan` — Monster/Tower/Skill/Buff/Map/future Quest/Recipe/Artefact — shows up automatically, searchable by asset name, with no editor-code change needed), and edits the selected asset through a live `SerializedObject`/`InspectorElement` binding — edits are real edits to the `.asset` file, not a separate copy. `Tools/TowerDefence/Run Event Chain Smoke Test` (`EntityEventChainSmokeTest.cs`) exercises the Entity/Skill/Trigger/Damage pipeline end to end with no scene/Play Mode required. `Tools/TowerDefence/Run Map Smoke Test` (`MapSmokeTest.cs`) does the same for `TowerDefence.Map` — string parsing, Dijkstra connectivity, Lane pairing, `MapPlan.LaneAssignments`, the random generator, and world-space `Node` positions — logging PASS/FAIL per section rather than needing tiles eyeballed in the Scene view.

`Tools/TowerDefence/Generate Example Content` (`ExampleContentGenerator.cs`) builds every example asset under `Assets/Examples/` in one pass: monsters (Slimey — has `SplitOnDeath`, DireWolf), 5 basic Towers + 2 fusion-result Towers (Opal = Ruby+Sapphire+Emerald, Garnet = Topaz+Amethyst+Ruby — see Fusion above), their projectiles/skills, a 16×16 `TestMap` (generated via `GenerateSerpentineMapRaw`, not hand-typed — width-1 corridor, Source fixed at (1,1)), the shared `MapContainer` prefab (generic, not test-specific) + one `TilePrefab`, and a full 20×20 first-Stage `WaveUtil.ENEMIETRIX[Forest]` (formulaic pacing, not tuned). Re-run after any Editor domain reload — `WaveUtil.ENEMIETRIX` is a plain static `Dictionary`, so that part doesn't persist as a saved asset the way everything else does.

### Testing / MVP demo

No committed scene sets this up (deliberately — see the git history around `GetOrCreatePrefab`'s scratch-GameObject churn desyncing the Scene Hierarchy TreeView, a Unity Editor UI bug, not a project bug). Build a scene by hand: one GameObject with `TickManager`, `EntityManager`, `GameManager`, `EntityWaveManager`, `HudDisplay`, `MvpDemoSpawner`, `UpgradeMenu`, `MainMenu` all added, then on `MvpDemoSpawner` assign `TowerPrefab`/`TowerPlan`, `MonsterPrefab`/`MonsterPlan`, `MapContainer`/`MapPlan` (the generated `MapContainer` prefab + `TestMap`), `AvailableTowers` (every Tower `Mulligan`/`FusionUtil` should see), and `UpgradeMenu`; on `MainMenu` assign `UpgradeMenu` too. `MvpDemoSpawner`'s own IMGUI panels (top-left: map/spawn/wave controls; below: Mulligan) plus `HudDisplay` (top-right: Gold/World-Biome-Stage-Round-Wave/DPS/every live Tower+Monster's HP) plus `MainMenu` (a nav bar across the very top) are the whole interactive surface — no Canvas/EventSystem/UGUI anywhere yet, all straight `OnGUI`.

`BasicMonster`/`BasicTower` also work with zero of the above: `MonsterController`/`TowerController` each have a `DefaultPlan` (Slimey/Ruby) and self-`Init` from it in `Start()` if nothing called `Init` first, so dropping either prefab straight into any scene "just works" for a quick check. `Util.Debug.LogManager.Instance` is lazily self-creating now too (a missing `LogManager` in the scene used to turn every `LogWarning` call into a `NullReferenceException` instead of showing the actual message) and mirrors every `Log`/`LogWarning`/`LogError` to Unity's real Console, not just its own internal `GetLogString()` readout.

### Naming convention

Design-time data classes are `I<X>Plan : IPlan` (`IEntityPlan`, `IPlan` itself giving `Guid`/`Name`) — not `<X>Data`. New Plan types should follow this so they're picked up uniformly (including by the Entity Data window above).

### Known gaps (worth checking before assuming something works)

- `AuraSpreading` (an aura-satellite relaying its Aura further outward) is still an unbuilt stub — only a source's own non-instance Aura ever propagates.
- `RaceCondition`'s constructors are empty (never stored which Race/Type to check) and `ConditionType.Race` isn't handled in `EntityUtil.Check` either — there's no clean "Towers only"/"Monsters only" condition to gate an Aura (or anything else) with yet; `WhetstoneAura`'s example content is missing this restriction as a result (it'll buff a nearby Monster too).
- `StatActionHandler`'s permanent mods and Foundry/Passive mods share one registry now, but anything still calling `StatBlock` mutation methods directly bypasses the dirty-flag cache.
- Status stacking archetypes (Fire/Poison/Debilitating/Disease) are a first pass, not a tuned balance — see Status Stacking above.
- No `Resources/Status/` `BuffPlan` assets have been authored — every `StatusType` falls back to `SkillsLib.GetStatusPlan`'s in-memory placeholder (a Name only, no real Effects).
- Fusion's hand+field case (`FusionMatch.FromField`) is detect-only — no code path actually consumes a field Tower and places the fused result yet (see Fusion / Mulligan above).
- Ranking (`TowerPlan.rank`/`NextRank`/`PreviousRank`) is unwired entirely — no purchase/trigger advances a Tower from one tier's Plan to the next (see Upgrade Menu above).
- A Monster reaching the Destination (`TriggerType.OnReached`) has nothing listening for it beyond `EntityWaveManager`'s own alive-count — no player-HP/lives cost or other consequence exists yet.
- `Util.Objects.IObjectPool<T>` is a pre-existing, completely empty interface (no members) — no pooling exists anywhere (Monsters/Towers/Projectiles/tiles are all plain `Instantiate`/`Destroy`). Don't assume pooling is wired just because the interface file exists.
